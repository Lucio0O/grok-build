# 07 权限、安全与沙箱

Grok Build 能改你的文件、跑你的命令。安全产品不是「加一个确认按钮」就结束，而是**好几道互相不替代的闸门**。本章讲每道闸门管什么、怎么叠、企业怎么锁。

---

## 先记住一句话

**批准发起 ≠ 内核允许碰到。**

- **权限**：对话策略。问不问人、规则允不允许、钩子拦不拦。
- **沙箱**：操作系统策略。这个进程和它拉起的命令，内核让不让读/写/联网。
- **文件夹信任**：项目里的可执行扩展（Hooks、项目 MCP、项目 LSP）默不默认跑。
- **密钥与日志**：出去的遥测和崩溃报告会脱敏；凭证文件权限收紧。

只开沙箱却把权限调成一律放行，模型仍可能在允许写入的目录里大改。只设权限却不开沙箱，一旦批准了一条宽命令，进程在内核看来仍几乎全能。两道要一起设计。

---

## 一次工具调用怎么被放行

顺序固定，后面的关卡不能推翻前面的「拒绝」。

```text
1. 使用前钩子（PreToolUse）
   钩子可以拒绝。钩子说「允许」并不跳过后面，只表示它不反对。
   钩子崩溃或超时：默认放行（以免钩子把主流程焊死）。要「失败即拒绝」需显式设计。

2. 权限规则
   拒绝 > 询问 > 允许。来源不重要，动作重要。
   全局拒绝不能被项目允许推翻。

3. 记住的批准
   用户以前对这个项目点过「以后都允许」。危险命令名单上的仍会再问。

4. 内置只读自动放行
   读文件、列目录、搜索、网页搜索、待办、任务控制、调用技能等。

5. 当前许可模式
   默认：没覆盖的就问人。
   别问我：没覆盖的就拒绝（适合 CI）。
   一律放行：没被规则/钩子拦住的就过。
   接受编辑：改文件自动过，其它仍按默认。
```

一律放行**不会**关掉拒绝规则、钩子，以及针对命令片段的「必须询问」规则。它也**不咨询**「记住的永远不允许」。规划模式则是另一套：除计划文件外，编辑直接失败。

无头里「本该问人」的调用不会挂起等输入，而是取消并告诉模型。所以 CI 的正确姿势是「别问我 + 窄允许」，不是「默认模式 + 盼着有人点」。

---

## 许可模式怎么理解

| 模式 | 人话 | 典型场景 |
|---|---|---|
| 默认 | 没把握就问 | 个人日常 |
| 别问我 | 没写允许就拒绝 | CI、高安全 |
| 一律放行 | 少打断，规则和钩子仍在 | 受信任的本机 |
| 接受编辑 | 改文件顺畅，跑命令仍谨慎 | 「你改代码我来跑」 |
| 规划 | 兼容名；真正规划是单独功能 | 先写 plan.md |

企业若不允许员工开一律放行，应在**系统级硬性要求**里锁，而不是写在用户自己能改的偏好里。用户家目录里的硬性文件挡不住会改文件的人；`/etc` 下由管理员拥有的文件才是组织锁。

## 规则写在哪、怎么合并

规则可以来自：

- 命令行重复的允许/拒绝
- 用户 `~/.grok/config.toml`
- 仓库里从根到当前目录的每一层 `.grok/config.toml`
- 兼容的 Claude 设置文件（含本机不提交的 local）
- 组织托管配置

合并后只看动作强弱：**拒绝强过询问，询问强过允许**。所以「全局拒绝删除类命令」是有意义的组织策略；「项目允许一切」盖不住它。

托管配置里的「允许一切」在一律放行被锁死时会被忽略，避免管理员锁了开关、托管文件又把大门打开。

### 命令规则的坑（必须写进安全说明）

- **拒绝/询问按段看**，`允许` 往往匹配整串。于是「允许 `git status`」不应被理解成「允许 `git status && 危险命令`」自动过关——后半段仍要过自己的检查。
- 文档明确警告：不要用「允许某个前缀」表达「只允许这一种事」。只许 git/gh 的正确方法是「别问我 + 只写这两类允许」，或用使用前钩子做白名单。
- 读/改的拒绝可以延伸到「这条命令会不会碰到这些路径」，包括套一层 `bash -c` 的脚本。
- 沙箱一旦生效，部分命令可以自动批准，因为内核已经围住了——这是叠加，不是替代规则。

### 规则能写到的种类（概念）

命令、读、改、搜索、网页抓取（可带域名）、网页搜索、MCP 工具（按服务器和工具名）。写规则时用种类和模式，而不是「第 37 个内部函数名」。

## 交互批准记在哪

用户点「以后都允许」时，记录在 Grok 内部、按项目分范围，**不进仓库**，避免把个人习惯提交给同事。危险名单上的命令即使有前缀记忆也会再问。

这和「把允许规则写进 `.grok/config.toml` 提交给全组」是两条路：前者是个人顺手，后者是团队政策。

---

## 沙箱：内核围栏

默认关。打开后，用操作系统原语限制**当前 Agent 进程及其子命令**（Linux 上是一类强制访问控制，macOS 上是席位隔离）。围栏在进程活着期间有效，不能中途拆掉。

### 内置档位

| 档位 | 能读 | 能写 | 子进程网络 | 适用 |
|---|---|---|---|---|
| 关 | 不限 | 不限 | 不限 | 完全信任的本机 |
| 工作区 | 到处 | 当前目录、Grok 家、临时目录 | 允许 | 日常开发推荐 |
| 开发盒 | 到处 | 除少数系统卷外的顶层目录 | 允许 | 一次性虚拟机 |
| 只读 | 到处 | 仅 Grok 家和临时目录 | Linux 可拦 | 审代码、只探索 |
| 严格 | 当前目录和必要系统路径 | 当前目录、Grok 家、临时目录 | Linux 可拦 | 不信任的代码 |

子进程网络拦截在 **Linux 上落实，macOS 上是空操作**。对外一定要写这句话，否则「严格档 = 不能上网」在 Mac 上不成立。

Grok 自己去调模型、搜索、抓取，通常仍走进程内 HTTP，不受「子进程网络」那一刀影响。要断这些，走网络策略或关功能，而不是只开沙箱。

### 自定义档

可以在家目录或项目里写沙箱配置：继承某个内置档，再加只读路径、可写路径、内核级拒绝列表（例如所有 `.env`、所有密钥文件）。内置名字不能被同名自定义悄悄换掉。

恢复旧会话时，沙箱档跟当时走，不跟这次命令行的新参数走。

### 钩子目录的写保护

工作区 / 只读 / 严格档会让 Grok 家目录整体可写（会话要落盘），但**内核禁止改写全局钩子目录**。避免 Agent 改自己的门禁。开发盒档不考虑这点（虚拟机本来就扔）。

## 文件夹信任

项目里的 Hooks、MCP、LSP 能跑代码或拉起外部进程。第一次打开这样的项目，需要用户明确信任（或启动时带信任）。记录在统一的信任名单里，对子目录连锁生效。

关掉「文件夹信任」功能，等于项目级这些扩展一起放开——这是给特殊环境的总闸，不是更安全，是更省事。默认应保持开启。

个人家目录里的钩子视为已信任：那是用户自己放的。

---

## 危险操作与「安全命令」清单

产品内置一份「看起来只读」的命令清单（看目录、看 git 状态、看日志等）。它们在默认和「别问我」下都可以自动过，除非规则或钩子反对。

清单用词边界匹配，避免 `ls` 误伤到别的命令。一些「看着像只读、其实会跑仓库代码」的东西（例如会执行构建脚本的检查命令）不在清单里。带预处理器的搜索、会加载可执行 git 钩子的配置，会抬高门槛再问一次。

## 和企业策略怎么配合

组织常见组合：

| 意图 | 权限 | 沙箱 | 其它 |
|---|---|---|---|
| 员工日常 | 默认 + 小组允许 | 工作区 | 信任本团队仓库 |
| CI | 别问我 + 窄允许 | 严格或自定义拒绝 | 无头、轮次上限 |
| 审不信任的补丁 | 只读规则 | 只读或严格 | 不要开子代理写文件 |
| 禁止 YOLO | 硬性要求锁开关 | 随意 | 系统级文件，不要只写用户文件 |
| 接内部 MCP | 对服务器名询问或拒绝 | 工作区 | 项目要信任；凭证单独存放 |

托管配置和硬性要求的层次见 [12](12-配置认证与企业治理.md)。

## 规划模式在安全里的位置

规划不是许可模式表上的一个普通值，而是：

- 任何许可模式下，非计划文件的编辑都失败
- 一律放行也失败
- 通过 shell 重定向写其它文件**不会**被这层拦住——所以规划不是沙箱替代品
- 子代理有自己的规划状态，**默认不受父会话规划门闩约束**

若方案是「先规划再动手」，又派了会写文件的子代理，等于开了后门。产品/安全评审要单独看这一条。

---

## 读完本章你应该能讲清

- 四道闸：钩子、规则、许可模式、沙箱（外加信任和脱敏）。
- 拒绝永远强于允许；无头不会等人点。
- 沙箱档位和网络拦截的平台差异必须写进说明。
- 规划、YOLO、子代理写文件，是三处常见误配。
