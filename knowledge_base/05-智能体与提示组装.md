# 05 智能体与提示组装

用户以为自己只是「和一个叫 Grok 的助手说话」。实际上，每一轮送给模型的系统提示，是按明确配方临时拼出来的。这一章讲配方：谁来决定「这个会话是谁」、材料从哪来、怎么覆盖。

---

## 两个容易混的词

| 词 | 是什么 | 能不能拷贝到另一个会话 |
|---|---|---|
| **智能体定义（Agent Definition）** | 一份 Markdown 配置：名字、何时用、工具白名单、系统提示正文 | 能。就是磁盘上的 `.md` 文件 |
| **智能体实例（Agent）** | 定义 + 当前工作目录 + 已经渲染好的提示 + 已经接好的工具 | 不能随便挪。它绑在这一次会话上 |

产品上对用户说「Agent」时，多半指定义或档位（`grok-build`、`explore`）。实现上，会话开工时才会把定义建成实例。

---

## 默认人格：grok-build

日常写代码用的就是内置档 `grok-build`。它的提示模式是「扩展」：先有一份统一的底座（怎么调工具、怎么排版、当前用户环境），再接上这份档自己的人格段落。

底座存在的意义是：无论谁写自定义 Agent，都不必重写「读文件要用哪个工具名」这类容易过期的约定。作者只写「你是代码审查员，按严重程度组织意见」。

另有内置 `browser-use` 等档，提示模式是「全量」：作者自己提供整份系统提示，用模板变量填工具名和环境。适合高度定制、不希望底座掺和的场景。

---

## 定义文件长什么样（概念）

一份定义通常是：

```text
---
名字、描述、工具列表、许可模式、要预装的技能……
---

下面是给模型看的人格和要求。
```

对产品重要的旋钮：

| 旋钮 | 人话 |
|---|---|
| 提示模式 extend / full | 接在底座后面，还是整份重写 |
| 工具白名单 / 黑名单 | 这个人格允许干什么；黑名单优先 |
| 许可模式 | 默认、接受编辑、别问我、规划…… |
| 是否注入 AGENTS.md | 默认为是。关掉则这个人格不吃项目宪法 |
| 输出风格 | 普通或更短 |
| 必须调用的收尾工具 | 编排场景里：不打招呼结束会被提醒继续 |
| 技能预装 | 一开场就把某些 playbook 放进上下文 |

未知字段会被忽略。这是为了新版本写的定义在旧二进制上不炸——前进兼容。

## 系统提示是怎么拼出来的

### 扩展模式（默认）

```text
底座模板
  · 工具约定、格式、当前操作系统/目录/日期
  · 后台任务等运行时说明
+ 定义文件正文（人格）
+ 项目规则（AGENTS.md 家族，若开启）
+ 技能目录与命中的技能正文
```

### 全量模式

```text
作者写的整份模板（可引用工具名、系统信息）
+ 项目规则（若开启）
+ 技能
```

子代理通常用更瘦的底座，避免每个孩子都带一份和主会话一样厚的说明书，浪费窗口。

### 材料来源优先级（智能体定义本身）

找「这个名字的 Agent」时：

1. 从当前目录往上走到仓库根，看 `.grok/agents/*.md`（离得近的优先）
2. 用户家目录 `~/.grok/agents/`
3. 兼容目录（例如其他助手的 agents 文件夹，可关）
4. 内置档

同名时，项目盖过用户，用户盖过内置。团队可以把「我们的审查员」放进仓库，覆盖个人同名定义。

## 项目规则：仓库宪法

`AGENTS.md`（以及兼容的 `CLAUDE.md` 等）不是配置开关，是**给模型看的说明**。它告诉 Agent：这个仓库用什么语言、测试怎么跑、什么能做、什么不能做。

发现规则：

- 家目录规则先装上（个人全局习惯）
- 再从仓库根走到当前目录，沿途所有匹配文件都装
- 越深的文件越靠后，冲突时以后者为准
- 每个目录还可以有 `.grok/rules/*.md` 这种规则夹

因此：根目录写「用 styled-components」，组件目录写「用 CSS Modules」，在组件目录里干活时，后者生效。这是刻意的「近处覆盖远处」。

项目规则**没有信任门**。它只是文本，不执行代码。这和 Hooks / 项目 MCP 不同。把「规范」放进 AGENTS.md，把「可执行门禁」放进 Hooks。

用户也可以在命令行用 `--rules` 临时加一段，只作用于这一次进程，不写进仓库。

---

## 技能：按需打开的手册

技能是带 `SKILL.md` 的目录。描述字段告诉模型「什么时候该用我」。用户也可以打 `/技能名` 强制启用。

和项目规则的差别：

- 规则：**每次**都在，像宪法
- 技能：**相关才打开**，像某道工序的作业指导书

技能还可以指定自己想用的模型、是否带附件。发现路径很多，并且默认兼容 Claude / Cursor 的技能目录，避免团队为 Grok 再抄一份。可用配置关掉某个厂商的扫描。同名技能高优先级覆盖低优先级。

插件可以整包带来技能，见 [13](13-扩展体系.md)。

## 提示里还有哪些「悄悄塞进去」的东西

除了人格和规则，一轮开始前后还可能注入：

| 注入 | 目的 |
|---|---|
| 用户环境块 | 模型知道 OS、shell、工作目录、今天日期 |
| 记忆检索片段 | 跨会话相关事实（功能开启时） |
| 系统提醒 | 「你该做完任务却没调用收尾工具」「发现了新技能」 |
| 生命周期贡献者文本 | 实验功能或企业逻辑在采样前追加的短句 |
| Goal / 规划纪律 | 目标模式和规划模式的额外约束 |

这些注入对用户不一定逐条可见，但会影响模型行为。产品上如果有人抱怨「它怎么突然变得这么严」，先看是不是 Goal 纪律或规划模式，而不是模型换了。

## 模型怎么被选中

选择是分层的，高的赢：

1. 这一次命令行或 `/model`、选择器
2. 技能头信息里指定的模型
3. 智能体定义或角色/人格上的默认
4. 配置里的全局默认
5. 内置目录里写死的默认（通常是 `grok-build` 编码模型）

另外还有专用默认：网页搜索、图像、会话摘要可以各用各的模型。运营活动可以临时改默认，用户关掉该活动后恢复。

「推理力度」(`/effort`) 是另一条轴，和选哪个模型正交：同一个模型可以少想一点或多想一点，以菜单披露的档位为准。

自定义端点（公司网关、Ollama、兼容 OpenAI 的服务）走配置里的模型块，见 [12](12-配置认证与企业治理.md)。

## 内置档和子代理可见性

主会话能选的档，和「任务工具能拉起来的子代理类型」不是同一张表。

对子代理，内置保证三类对用户和模型同时可见、同时可调：

- `general-purpose`：全能
- `explore`：只调查，不改文件
- `plan`：只做方案，不改文件

用户可以用配置关掉某类，也可以用同名定义盖住内置。产品不变量是：**菜单上看得见的，模型就调得起**；不要出现「设置里开着、工具却找不到」的裂缝。

编排型内置档会明确要求主代理多委派、少自己浅读。这是在推「主代理做指挥、子代理做专项」的工作方式，见 [09](09-子代理与协作.md)。

---

## 组装失败时用户会看见什么

定义写坏（缺名字、YAML 烂、模板变量算不出来）时，建档失败，会话起不来或那个自定义档不可用。业务上应引导用户去 `/config-agents` 或检查 `.grok/agents/`，而不是报一团内部错误。

工具名覆盖如果指向不存在的工具，同样失败——这是为了避免「模型以为有这个工具，其实没有」的幻觉接口。

## 产品设计含义

1. **人格可版本管理。** 定义是 Markdown，能进 git，能做代码评审。
2. **底座统一，人格分开。** 降低自定义 Agent 的维护成本，也降低「每个人自己发明一套工具用法」的风险。
3. **项目规则近处优先。** 大单体仓库里不同子树可以有不同宪法。
4. **技能按需。** 避免把所有作业指导书一次性塞进窗口。
5. **子代理用瘦提示。** 并行多个孩子时，窗口和费用都更可控。

---

## 读完本章你应该能讲清

- 定义是文件，实例绑会话。
- 系统提示 = 底座或全量稿 + 规则 + 技能 + 运行时注入。
- 规则始终在，技能按需在。
- 模型选择和人格选择是两条轴，偶尔交叉。
