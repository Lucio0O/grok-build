# 10 计划、目标、工作流与后台节奏

普通对话适合「边想边干」。当事情变大、变长、变不确定，产品提供四条专门的轨道。它们不是同一个功能的四个名字，而是四种**控制节奏的方法**。

| 轨道 | 解决的问题 | 谁驱动继续 |
|---|---|---|
| **规划模式** | 先对齐方案再动工 | 人批准 `plan.md` |
| **目标模式** | 必须真正做完，不能口头交差 | 宿主每轮核查证据 |
| **工作流** | 多阶段、多 Agent、要可重放的脚本 | Rhai 脚本 + 宿主 |
| **后台 / 循环 / 监视** | 活要挂很久，人还要继续聊 | 任务完成或到点叫醒 |

---

## 规划模式：先施工图，后开工

### 思路

有些任务方案有好几条合理路线（鉴权选型、缓存放哪、实时通道用什么）。先写代码再争论，返工成本高。规划模式强制：

1. 只读探索（外加可以写计划文件）
2. 把推荐方案写进本会话的 `plan.md`
3. 必要时结构化地问用户
4. 交卷时弹出预览，等人批准、批注或打回

计划文件典型包括：为什么改、推荐做法（不是把备选方案写满）、关键路径、可复用的现有函数、怎么端到端验收。

### 怎么进去

- 模型自己判断「这事有真分歧」，申请进入——要用户点头，拒绝则继续普通模式
- 用户 `/plan` 或 `Shift+Tab` 转到规划；下一句提示才真正激活（或 `/plan 描述` 一句话同时激活）

不适合规划的：改错字、加一颗按钮、用户明显想马上动手。产品提示词里也这样教模型，避免「什么都先开会」。

### 状态

| 状态 | 含义 |
|---|---|
| 未启用 | 普通干活 |
| 待生效 | 用户打开了开关，还没发出下一句 |
| 已启用 | 只能改计划文件，改别的文件失败 |
| 退出待定 | 一轮还在跑，用户已关掉规划，等这轮结束再恢复普通 |

一律放行也改不了非计划文件。空计划交卷仍会打开预览，避免「没写就假装过关」却让用户没处点。

批准后可以用合成轮接着实现；`/view-plan` 可以再打开已保存的预览。

### 规划不是沙箱

命令重定向写其它文件、以及子代理写文件，规划层不管。规划是**产品流程约束**，不是内核围栏。高风险仓库请叠加权限和沙箱。

## 目标模式：做完为止，而且要有证据

`/goal` 让用户放下一个目标，例如「把鉴权模块迁到新 API」。和普通对话的差别是**完成标准**：

- 模型不能只说「我做完了」
- 宿主在每一轮模型结束后评估：是否像做完了
- 像做完了，就交给**唱反调的核查**看证据
- 核查复现不了、或证据不够，目标继续或暂停，并列出缺口
- 只有核查承认，才标成完成

这和本知识库开头那条「Goal 指令」的精神一致：完成必须经得起一条条对质，不能靠态度或摘要。

### 用户能做的

- 设立目标，可选带**额度预算**（这里是 token 预算，和工作流的「能请几个 Agent」不是一笔账）
- 看状态、暂停、继续、清除

后台工作流开关影响具体司机：开着时由宿主评估每一轮并做对抗核查；关着时走旧的「模型自己汇报进度、再触发核查」。对用户，命令一样。

### 纪律（产品性格）

目标提示会要求：

- 自己做完用户要的一切，不要把手工步骤甩回用户
- 用待办拆步，始终有一步进行中
- 在真实路径上验证，禁止「测试演戏」（测试通过但产品仍坏）
- 用目标私有的草稿目录放临时输出，目标结束就删
- 真有外部卡点，要写清证据和需要人做的那一下；宿主按「反复同一卡点」策略处理

对外可以说：Goal 是「带验收的自动驾驶」，不是「更长的聊天」。

## 工作流：可编程的多 Agent 剧本

当步骤稳定、要复用、要并行、要预算时，用工作流，而不是每次靠模型即兴委派。

- 剧本是脚本文件：项目 `.grok/workflows/`，用户 `~/.grok/workflows/`
- 引擎按剧本请宿主去真正拉起 Agent，自己不拥有模型循环
- 有阶段、并行上限、Agent 个数预算、暂停种类
- 运行过程记日记，便于同进程内按已提交结果重放

用户侧：

- `/workflow 名字 {参数}` 启动
- `/workflows` 看进行中的（显示名，重名会自动编号）
- 暂停 / 继续 / 停止 / 另存

继续的语义偏严，产品必须写进说明：

- 同进程暂停后续跑，用的是**当初那份不可变剧本和预算**
- 想改剧本，应编辑副本再开新跑
- 触达预算的跑，不能靠一句「继续」偷偷加名额
- 进程重启后不接着跑：外部副作用没有跨进程的稳定身份
- 继续不是恰好一次：暂停前没提交的外部动作可能再执行一遍

工作流结束会合成一轮叫醒主会话。深度研究（`/deep-research`）对用户是「丢进去就回来」，进度在工作流列表里，报告自己出现在对话中——它是这条轨道上的一个产品包装，不是第五条轨道。

## 后台命令、循环、监视

### 后台命令

长编译、测试、开发服务器不该堵住对话。模型可以一上来就后台启动；用户也可以把已经在跑的前台命令降到后台。完成时通知，必要时叫醒一轮。

配套：取输出、等多个、杀掉（先温和再强制；对子代理则是取消和关闭）。

### 定时循环

`/loop` 按间隔把同一句话再问一遍。适合「部署好了没」。间隔有下限，任务有个数和过期，避免无限定时器堆满机器。到点就是一次合成轮。

### 监视

按行看日志。适合「失败那一行一出现就叫醒」。往往要求被监视的命令行缓冲输出，否则行会攒在一起，监视失去意义——这是给高级用户的使用条件，不是 bug。

任务面板是这三类加上子代理的汇总入口。Dashboard 行在「还有后台活」时保持工作中。

## 四条轨道怎么选（决策表）

| 你听到用户说 | 用 |
|---|---|
| 「先别写代码，我们看看几种做法」 | 规划 |
| 「在我回来之前必须做完，而且要真的能跑」 | 目标 |
| 「我们组每周都要跑同一套审查/发布步骤」 | 工作流 |
| 「先把测试挂上，我们继续改」 | 后台 |
| 「每半小时看一眼预发」 | 循环 |
| 「日志一报错就叫我」 | 监视 |
| 「一边查代码一边写」 | 普通对话 + 子代理 |

可以组合：规划批准后进入目标；工作流内部再请子代理；循环叫醒后仍走普通工具。组合时把「谁有权宣布完成」讲清：规划听人，目标听核查，工作流听剧本，后台听进程退出码。

---

## 读完本章你应该能讲清

- 规划管「先对齐」，目标管「验收」，工作流管「剧本」，后台管「挂着」。
- 规划不代替沙箱；目标不相信自述；工作流继续有严格限制。
- 合成轮是这四条轨道共用的「闹钟」。
