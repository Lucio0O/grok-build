# 01 产品定位与全貌

## 一句话

**Grok Build** 是 SpaceXAI 做的**终端里的 AI 编程助手**。它不只是「能在终端里聊天」，而是一台会读代码、改文件、跑命令、搜网页、拆任务、带一班子代理干活的**智能体运行时**。用户安装后，命令名是 `grok`。

官方介绍见仓库根目录 `README.md`：它以全屏终端界面运行，也能无界面跑在脚本和 CI 里，还能通过 Agent Client Protocol（ACP）嵌进编辑器。

---

## 它解决什么问题

开发者日常写代码时，真正耗时间的往往不是「想一句回复」，而是一整条工作链：

1. 搞清仓库里现有约定和相关代码在哪
2. 拟定改法，并和同事（或自己）对齐
3. 改多个文件、跑测试、看失败、再改
4. 同时盯着构建、开发服务器、外部系统
5. 过几天还要接着昨天的上下文继续

Grok Build 把这条链收进一个进程：用户用自然语言下任务，运行时负责理解仓库、调用工具、把结果流式展示出来，并在需要时停下来问人。

它和「网页里的编程助手」的关键差别是：**它住在用户的机器上，直接碰工作区文件和本机命令**。模型在云端思考，手脚在本地。

---

## 三种用法，同一套大脑

产品对外提供三种入口，背后是同一套会话与工具运行时。

| 用法 | 用户怎么打开 | 适合谁 | 交互方式 |
|---|---|---|---|
| **交互终端界面（TUI）** | 在项目目录里输入 `grok` | 日常开发 | 全屏对话、权限弹窗、快捷键 |
| **无头 / 脚本（Headless）** | `grok -p "解释这个仓库"` | CI、自动化、一次性任务 | 跑完打印结果就退出 |
| **Agent 模式（ACP）** | `grok agent stdio` 等 | IDE、自研宿主、网页中继 | 结构化消息，长驻进程 |

可以把它想成：

- TUI 是「给人对着说话的驾驶舱」
- Headless 是「给脚本打电话的客服窗口」
- ACP 是「给编辑器对接的标准插座」

驾驶舱、窗口、插座可以换，发动机（会话、模型循环、工具、权限、持久化）是同一台。

---

## 产品不是什么

为了避免和邻近产品混淆，先划清边界。

**它不是网页版 Grok Chat。** Chat 侧重对话与内容生成；Build 侧重「在真实代码库上闭环干活」。两端会共用一些底层能力（例如上下文压缩引擎），但产品策略不同：Build 默认把整段过长历史**摘要后整段替换**，并深度绑定文件、Git、沙箱、权限。

**它不是单纯的补全插件。** 补全回答「下一行写什么」；Build 回答「这件事怎么从头做到验收」。

**它不是远程云开发环境本身。** 默认情况下，文件和命令发生在用户本机（或用户指定的工作目录）。云端主要提供模型推理、账号、部分托管配置和中继。计算机使用、浏览器操作如果出现，通常来自外部 MCP 工具或宿主环境，而不是 Build 内置的「打开 Chrome」一等工具。

**它目前不接受外部贡献。** `CONTRIBUTING.md` 写明外部贡献不被接收。本仓库是内部单体仓库的同步切片。

## 用户能感知到的核心对象

读后面章节时，请始终抓住这几个对象。它们是产品语言，不是实现细节。

### 会话（Session）

一次完整对话及其产生的状态：用户消息、模型回复、工具记录、待办、计划稿、回退点、用量。会话会自动落到磁盘，可以恢复、分叉、回退、压缩。详见 [04](04-会话与一轮对话.md)。

### 一轮（Turn）

用户（或系统）投入一条提示之后，模型「思考 → 调工具 → 再思考」直到本轮结束的全过程。一轮里可能发生十几次工具调用。后台任务完成、子代理结束、定时器触发，也可以自动开启一轮——产品里叫**合成轮**，不是用户刚敲进去的那句话。

### 工具（Tool）

模型不能自己改磁盘，它只能申请执行工具。宿主检查权限和沙箱后，才真正去读文件、改文件、跑命令。工具清单见 [06](06-工具与能力地图.md)。

### 智能体档（Agent Profile）

一套「这个会话是谁、会什么、用什么系统提示」的配置。默认档叫 `grok-build`。还可以定义代码审查员、探索员、规划员等。子代理也是一种智能体档。详见 [05](05-智能体与提示组装.md) 与 [09](09-子代理与协作.md)。

### 工作区（Workspace）

当前目录代表的那份代码、Git 状态、文件变更记录和检查点。Agent 的手脚长在工作区上。详见 [08](08-工作区与代码变更.md)。

### 权限与沙箱

两道独立闸门：

- **权限**决定「能不能发起这件事」（要不要问人、规则允不允许）
- **沙箱**决定「进程就算跑起来，内核允不允许碰到那些路径和网络」

详见 [07](07-权限安全与沙箱.md)。

## 一次典型任务长什么样

以用户说「给登录接口加上限流」为例，产品内部大致经历：

```text
用户输入
  → 会话收下这条提示（或先排进队列）
  → 拼好系统提示：人格 + 项目规则 + 可用技能 + 当前目录信息
  → 模型阅读仓库（读文件、搜索、列目录）
  → 必要时进入规划模式，只写 plan.md，等人批准
  → 按批准的方案改文件、跑测试
  → 流式把思考、工具、差异显示在回滚区
  → 危险操作弹出许可
  → 一轮结束，状态写入磁盘
  → 上下文快满时自动压缩，或用户手动 /compact
```

用户看到的是连续的对话和工具块；产品经理需要知道：中间每一跳都有明确的策略点（问不问人、允不允许写、要不要委派子代理、要不要压缩）。

## 平台与发布形态

- **安装**：macOS / Linux 用安装脚本；Windows 用 PowerShell 或 Git Bash。预编译二进制对外叫 `grok`，从源码编出来的制品名是 `xai-grok-pager`。
- **更新**：`grok update`；也可在启动时自动检查。企业可用版本上下限锁住升级节奏。
- **构建**：Rust 工作区。根 `Cargo.toml` 是生成物，不要当手写源。
- **许可**：第一方代码 Apache 2.0。第三方与内嵌移植（含部分 Codex / OpenCode 工具实现、Mermaid 图栈）保留原许可。

## 和竞品同场时，Grok Build 的产品性格

不必做成功能对照表，抓住性格即可：

- **终端原生**：默认全屏 TUI，也提供极简模式（内容进终端原生回滚区）。
- **兼容其他助手的工作习惯**：能读 Claude / Cursor 的规则、技能、部分设置，欢迎页还能导入外部会话。目标是「团队已经有的仓库约定不要重写一遍」。
- **企业可锁**：组织可以下发托管配置和硬性要求，关掉「一律放行」、钉死版本、限制遥测。
- **扩展是五条平行通道**，不是一个插件商店打天下：项目规则、技能、插件、钩子、MCP。怎么选见 [13](13-扩展体系.md)。
- **完成标准偏严**：Goal 模式不会因为模型自称做完就收工，而要过一轮对证据的核查。

## 读完本章你应该能对外讲清

- Grok Build 是本机智能体，不是网页聊天窗口。
- 同一套运行时服务三种入口：人对着终端、脚本调用、编辑器嵌入。
- 产品对象是会话、一轮、工具、智能体档、工作区、权限/沙箱。
- 价值按「看见 → 动手 → 做大 → 做对 → 进组织」五层展开。
