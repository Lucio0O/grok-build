# 02 整体架构

本章回答：这个仓库在产品层怎么分层，一次用户请求经过哪些角色，各 crate 大致落在哪一层。不讲函数和锁，只讲**责任划分**和**协作方式**。

---

## 先建立一张地图

把 Grok Build 看成四层楼：

```text
┌─────────────────────────────────────────────────────────────┐
│  入口层   TUI / 无头 CLI / ACP 客户端 / Dashboard            │
├─────────────────────────────────────────────────────────────┤
│  编排层   Leader · 会话执行体 · 提示队列 · 生命周期钩子       │
├─────────────────────────────────────────────────────────────┤
│  智能层   智能体档 · 提示组装 · 模型采样 · 压缩 · 记忆        │
├─────────────────────────────────────────────────────────────┤
│  手脚层   工具 · 工作区 · 权限 · 沙箱 · MCP · Git/检查点      │
└─────────────────────────────────────────────────────────────┘
```

用户永远只碰到入口层。入口层把「人说的话」变成会话命令；编排层决定现在该不该跑一轮、跑哪一个会话；智能层决定对模型说什么、模型回了什么；手脚层决定磁盘和网络上真正发生什么。

仓库里的 Rust 包（crate）基本按这四层切开，方便独立编译和测试，对用户不可见。

---

## 入口层：三种门，一栋楼

### 终端界面（Pager）

`xai-grok-pager` 是驾驶舱：回滚区、底部输入框、弹层、主题、鼠标、语音听写。它**不执行工具**，只负责：

- 收集键盘、鼠标、粘贴、语音
- 把用户动作编成「动作」，必要时再变成「副作用」（发协议、读文件、画图）
- 把会话流式更新画成可读的 Markdown、差异、工具块

真正的 Agent 在另一边。Pager 通过 ACP 风格的通知接收思考、工具、权限请求。

二进制拼装根是 `xai-grok-pager-bin`：用户装到机器上的 `grok` 就是它编出来的。它还挂上极简渲染模式、Mermaid 子进程、麦克风采集子进程等「必须在主程序入口拦截」的旁路。

### 无头 CLI

`grok -p` 走同一套会话，但不画全屏界面。提示从命令行或文件进来，结果打到标准输出，进程结束。权限如果需要人点，默认不会傻等，而是取消并告诉模型——所以无头场景通常要配好允许规则或「不要问我」。

### ACP / Agent 模式

编辑器和自研宿主把 Grok 当成服务器：创建会话、送提示、收更新、答许可。传输可以是标准输入输出、本机 WebSocket，或经 grok.com 中继连到远程网页客户端。

---

## 编排层：一台 Leader，多个客户端

### 为什么需要 Leader

一台机器上用户可能同时开：一个终端 TUI、一个 IDE 插件、一条无头命令。如果每个窗口各自持有 Agent 状态，会话会打架，磁盘也会写乱。

产品选择是：**本机通常一个 Leader 进程**，持有共享的 Agent 与会话；TUI / IDE / 无头作为 Client 连上来。本地用 Unix 套接字；有 grok.com 会话时还可以再挂 WebSocket 中继给远程客户端。

可以把它想成「本机总台」：

- 总台负责会话生死、模型调用、工具执行、写盘
- 各个窗口只是话筒和屏幕
- 较新版本的客户端可以请旧总台让位（版本比较后替换），避免一台机器上永远停在旧二进制

### 会话执行体（Session Actor）

每一个会话是一个独立执行体：自己的对话历史、工具上下文、磁盘目录。总台把「新提示 / 取消 / 关闭」路由给对应执行体；执行体把「界面该更新什么」推回所有连着的客户端。

会话有一组用户能在 Dashboard 里看到的粗粒度状态：

| 状态 | 人话 |
|---|---|
| 正在工作 | 正在跑一轮，或后台任务/监视器/定时循环还活着 |
| 空闲常驻 | 这轮完了，但还挂在当前界面里，随时能接着说 |
| 休眠 | 长时间没人盯，内存里卸掉，磁盘还在 |
| 已完成 | 有明确结束标记 |
| 失败死亡 | 执行体异常退出 |

### 提示队列

用户不必等上一轮结束才能打下一句。新提示可以排队；「立刻发送」会打断当前轮。多条短提示在展示上可能被合并，以免界面上蹦出一串碎片。系统自动唤醒的合成提示一般不写进「用户提示历史」，部分也不会在回滚区回显成用户气泡。

## 智能层：对模型说什么、模型回什么

### 智能体档

一次会话开始时，宿主用 `xai-grok-agent` 把「定义文件 + 当前目录 + 工具桥」收成一个不可随便挪走的 `Agent` 对象：系统提示、可用工具、提醒策略、压缩策略、模型配置。

定义文件是带 YAML 头的 Markdown，放在项目 `.grok/agents/` 或用户 `~/.grok/agents/`。默认内置 `grok-build`（日常写代码）和若干子代理类型。详见 [05](05-智能体与提示组装.md)。

### 采样（Sampler）

`xai-grok-sampler` 负责对流式模型 HTTP 的调用：重试、取消、异常循环保护、鉴权失败后的一次刷新。它不关心 TUI 长什么样，只把模型事件交给会话。

支持三种常见 API 方言（聊天补全、Responses、Messages），所以自定义模型和兼容网关接得进去。详见 [12](12-配置认证与企业治理.md)。

### 对话状态

发给模型的那份「对话真相」由独立的对话状态执行体保管，而不是散落在界面里。界面看到的回滚区和模型看到的消息列表相关，但不保证逐字同一份：压缩、裁剪工具结果、注入系统提醒，都发生在模型侧历史上。

### 压缩与记忆

上下文窗口会满。满之前可以自动或手动把早期对话收成摘要（或指向更细的分段/全文）。跨会话的长期记忆是另一条可选通道，默认关闭。详见 [11](11-记忆压缩与上下文.md)。

## 手脚层：模型申请，宿主执行

```text
模型说出「请调用 search_replace」
        ↓
生命周期钩子可以否决
        ↓
权限规则 / 记忆中的批准 / 只读自动放行 / 当前许可模式
        ↓
工具真正执行（读盘、写盘、开进程……）
        ↓
操作系统沙箱限制进程碰得到的路径和子进程网络
        ↓
变更记入 hunk 追踪与回退检查点
        ↓
结果和提醒回到模型，界面同步更新
```

这一层的产品原则是：**授权不等于能力**。

- 权限系统回答「我们答不答应你发起」
- 沙箱回答「就算答应了，内核让不让你碰到」
- 工作区回答「当前目录、Git、检查点的真相是什么」

MCP 服务器提供的外部工具，会注册进同一套「计算机中枢」，模型通过发现+调用或限定名使用。内置工具和 MCP 工具对模型来说都是「可调用动作」，对治理来说规则语法不同。

## 一次提示的端到端旅程

下面是产品经理对外讲解时最有用的主路径。

```text
1. 入口收下输入
   TUI 回车 / 无头 -p / ACP session/prompt / 合成唤醒
2. 编排承认提示
   进队列，或插到队首并取消当前轮
3. 会话开始一轮
   解析斜杠命令、技能、附件；生命周期「轮次开始」
4. 组装提示
   智能体系统提示 + 项目规则 + 记忆片段 + 用户消息
5. 模型循环
   流式文本 / 思考 / 工具调用
6. 每个工具
   钩子 → 规则 → 批准 → 执行 → 沙箱边界 → 记录变更
7. 推界面
   session/update：文字块、工具块、权限请求、计划预览
8. 轮次结束
   记用量、考虑压缩、刷新记忆、处理队列下一条
9. 写盘
   权威日志 updates.jsonl + 模型侧 chat_history + 摘要索引
```

任何「用户觉得 Agent 自己做主了」的时刻，都可以在第 6 步找到闸门；任何「为什么过几天还能接着聊」都可以在第 9 步找到磁盘布局。

## 几个架构选择，以及它们对产品的含义

### 1. 界面与运行时拆开

好处：同一会话可以被 TUI 和 IDE 同时盯着；界面崩溃不一定毁掉 Agent。代价：必须有协议和重连。产品上表现为「Dashboard 里能看到别的窗口开着的会话」「断线后能把对话重新装回来」。

### 2. 每个会话一条执行线程

工具和会话状态不必在所有线程间传来传去。产品含义：一个会话卡死不应直接拖死所有会话；Dashboard 上的多个 Agent 是真并行，不是一个聊天框切来切去装出来的。

### 3. 工具走统一注册表，MCP 走中枢适配

内置能力和生态能力对模型是同类动作，对安全和配额却能分开治理。产品上可以卖「默认就会改代码」，也可以卖「再接公司内部 MCP，而不把内部工具写进 grok 二进制」。

### 4. 配置多层合并，企业要求最后再盖一次

远程运营活动（campaign）可以改默认模型或推功能，但不能压过管理员的硬性要求。详见 [12](12-配置认证与企业治理.md)。

### 5. 扩展点不拥有主循环

生命周期贡献者只能「在轮次前后塞数据或挂命令」，不能把主循环抢走。这保证 Memory、企业钩子、实验功能可以往上挂，而不把「一轮怎么跑」分叉成五份。

---

## 读完本章你应该能对外画清

- 四层：入口、编排、智能、手脚。
- 本机一台 Leader，多个窗口共用会话。
- 一轮 = 组提示 + 模型循环 + 带闸门的工具执行 + 写盘。
- 授权、沙箱、工作区是三件不同的事。
